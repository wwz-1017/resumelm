# ResumeLM 产品设计规格

- 日期：2026-05-21
- 项目：ResumeLM - AI 智能简历生成与优化平台
- 版本目标：8-12 周功能完整第一版
- 目标用户：校招大学生为主，兼顾 B 端招聘协作场景

## 1. 产品目标

ResumeLM 第一版的核心目标是帮助校招用户在无登录门槛的前提下，快速完成简历生成、优化、评分和导出，并让招聘侧可以基于岗位 JD 对简历进行匹配评分和协作评审。

第一版优先保证以下结果：

- 用户无需注册登录即可立即使用主要功能
- 用户可以完成从输入信息到导出 PDF/Word 的完整简历生产流程
- 平台可以基于规则引擎与 LLM 联合输出 ATS 兼容性、内容完整度和 JD 匹配评分
- 招聘团队可以在 B 端完成岗位维度的候选简历评分、评论和评审状态流转

第一版不优先解决以下问题：

- 长期账号体系与跨设备同步
- 英文与双语简历完整支持
- 支付与商业化闭环
- 高复杂度多租户企业管理后台

## 2. 产品原则

第一版遵循四个原则：

1. 低门槛：无需登录即可使用核心能力。
2. 低成本：优先采用能覆盖主要需求的最低复杂度方案。
3. 高隐私：默认不要求用户把简历上传到云端长期存储。
4. 高可演进：第一版虽然匿名开放，但后续可以平滑升级到登录体系和云端协作。

## 3. 用户与场景

### 3.1 C 端用户

主要用户是正在参加校招的大学生和应届生，需求包括：

- 从零生成一份适合校招的中文简历
- 对已有简历进行润色和关键词增强
- 针对目标岗位 JD 查看匹配度和改进建议
- 按模板编辑排版并导出 PDF/Word

### 3.2 B 端用户

第一版支持轻量招聘协作用户，典型角色包括：

- 招聘负责人
- 用人经理
- 面试官或协作评审人

需求包括：

- 录入岗位 JD
- 查看候选简历与岗位的匹配评分
- 给候选人简历添加评论和结论
- 管理评审流程状态

## 4. 范围定义

### 4.1 第一版包含

- 匿名开放访问
- 本地保存简历草稿
- 导出与导入简历 JSON
- AI 简历生成
- AI 工作经历润色
- 技能关键词推荐
- ATS 兼容性分析
- JD 匹配评分
- 简历结构化评分报告
- 在线简历编辑器
- 模板切换
- PDF/Word 导出
- B 端岗位管理
- B 端简历匹配结果查看
- B 端评审评论与状态流转

### 4.2 第一版不包含

- C 端登录注册
- 匿名用户云端长期保存
- 中英文双语全链路支持
- 企业复杂权限中心
- 支付订阅
- 智能面试、笔试、职位投递闭环

## 5. 核心产品决策

### 5.1 匿名开放策略

第一版的 C 端采用完全开放模式，用户无需注册登录即可使用简历生成、优化、评分与导出能力。

这样做的原因：

- 校招用户对即时可用的诉求高于账号沉淀
- 去除登录可显著降低首屏流失
- 首版研发应把资源集中在 AI 能力和简历体验，而不是用户体系

### 5.2 数据保存策略

第一版默认采用浏览器本地保存，不做匿名云端长期保存。

保存策略如下：

- 用户编辑中的简历草稿保存在 `localStorage` 或 `IndexedDB`
- 用户可手动导出 `JSON` 作为备份
- 用户可导入历史 `JSON` 恢复继续编辑
- 分享与投递场景通过导出 `PDF/Word` 完成

这样可以用最低成本覆盖大部分校招用户需求，同时规避匿名云端存储带来的会话管理、数据滥用、隐私合规和回收策略复杂度。

### 5.3 B 端数据策略

B 端不是匿名开放模式。B 端第一版允许通过内部受控方式录入岗位和评审数据，作为后续登录体系的预埋模块。

为了兼顾当前范围和后续扩展，系统分成两套数据路径：

- C 端匿名编辑数据：默认本地保存，不要求入库
- B 端岗位、评分、评审数据：存储在 Supabase/PostgreSQL

## 6. 总体架构

系统采用单体优先、模块化演进方案。

### 6.1 技术选型

- 前端：Next.js App Router
- UI：Tailwind CSS + 自定义编辑器组件
- 后端能力：Supabase + PostgreSQL + Storage + Edge Functions
- AI 层：统一 LLM Gateway
- 导出层：HTML/CSS 模板渲染 + PDF/Word 生成
- 部署：Vercel 或等价平台 + Supabase 托管服务

### 6.2 架构原则

- 业务先模块化，再考虑拆服务
- AI 调用必须通过统一网关，不允许页面直接连模型厂商
- 评分逻辑拆分为规则引擎与 LLM 评估器两个独立模块
- 编辑器、评分器、导出器之间通过标准化简历 JSON 通信

## 7. 系统模块

### 7.1 C 端匿名工作台

负责用户从输入信息到导出简历的完整体验，包括：

- 新建简历
- 导入 JSON
- 基础信息填写
- 教育、实习、项目、校园经历、技能等结构化编辑
- AI 辅助生成与润色
- JD 粘贴与匹配分析
- 评分报告查看
- 模板切换
- PDF/Word 导出

### 7.2 在线简历编辑器

编辑器采用结构化块模型，不以传统富文本为核心，而是以“简历数据结构 + 模板渲染”为主。

编辑器要求：

- 支持增删改排序
- 支持分块 AI 润色
- 支持手动编辑与 AI 结果二次修改
- 支持模板即时预览
- 支持结构校验，避免导出空块和错误字段

### 7.3 AI 简历助手

AI 助手包含以下能力：

- 从基础信息生成首版简历内容
- 对工作经历、项目经历进行成果导向润色
- 提取和推荐技能关键词
- 生成 ATS 改进建议
- 生成 JD 对齐建议

### 7.4 简历评分模块

评分模块基于规则引擎与 LLM 双通道评估，输出：

- 总分
- 分项分数
- 问题项清单
- 结构化改进建议
- 与 JD 的关键词覆盖说明

### 7.5 B 端岗位与评审工作台

第一版 B 端支持：

- 岗位 JD 创建与管理
- 候选简历与岗位匹配评分查看
- 候选简历评论
- 评审状态流转
- 评审结论记录

## 8. 统一 LLM Gateway 设计

### 8.1 目标

统一接入多家大模型服务，提供一致的调用协议、路由策略和容错能力。

### 8.2 支持能力

- `generate`：生成简历内容
- `rewrite`：润色和重写
- `evaluate`：评分和诊断
- `extract`：提取关键词、结构化字段

### 8.3 路由策略

按任务类型选择模型：

- 文案生成：优先高质量生成模型
- 结构化抽取：优先稳定 JSON 输出模型
- 评分分析：优先长上下文和强推理模型

### 8.4 容错机制

- 超时重试
- 主备模型切换
- 熔断
- 统一错误映射
- 响应 schema 校验
- 请求链路日志记录

### 8.5 成本控制

- 每次请求记录 token 使用量
- 对匿名用户设置频率限制
- 对高成本评分任务做请求节流和缓存

## 9. 数据设计

### 9.1 核心简历数据结构

为保证编辑、评分、导出三者共享同一份数据模型，C 端内部采用标准化简历 JSON 结构，核心字段包括：

- `profile`
- `education`
- `internships`
- `projects`
- `campus_experience`
- `skills`
- `awards`
- `target_job`

这份结构既是编辑器状态，也是 AI 输入输出和导出模块的标准载体。

### 9.2 PostgreSQL/Supabase 表设计

虽然匿名 C 端不默认入库，但 B 端和平台侧仍需要数据库。建议表如下：

- `organizations`
- `members`
- `jobs`
- `job_keywords`
- `candidate_profiles`
- `candidate_resumes`
- `resume_job_matches`
- `ats_reports`
- `review_tasks`
- `review_comments`
- `review_decisions`
- `ai_requests`
- `export_tasks`

### 9.3 权限策略

第一版权限边界：

- 匿名 C 端：不依赖数据库访问权限
- B 端：通过受控后台或内部账号访问数据库

后续如引入 Supabase Auth，可直接把 B 端表接入 RLS，并在第二阶段增加 C 端用户体系。

## 10. 评分与评估设计

### 10.1 评分维度

建议总分为 100 分：

- ATS 结构兼容：25 分
- 内容完整度：20 分
- JD 关键词匹配：30 分
- 成果量化表达：15 分
- 可读性与简洁度：10 分

### 10.2 规则引擎

规则引擎负责确定性检查，例如：

- 是否缺少基础字段
- 是否缺少教育经历
- 是否存在过长段落
- 是否缺少量化成果
- 是否缺少技能模块
- 是否缺少与 JD 相关关键词

### 10.3 LLM 评估器

LLM 负责非确定性分析，例如：

- 语义相关性
- 表达专业度
- 描述是否成果导向
- 项目经历是否有说服力
- 建议的优先级排序

### 10.4 输出格式

评分输出必须是结构化 JSON，至少包含：

- `overall_score`
- `dimension_scores`
- `issues`
- `suggestions`
- `matched_keywords`
- `missing_keywords`

## 11. 导出与模板系统

### 11.1 模板策略

模板系统基于统一简历 JSON 渲染，不同模板只负责视觉和布局，不改动业务数据结构。

第一版模板建议：

- 校招标准模板
- 极简单栏模板
- 稍强调项目经历的技术岗模板

### 11.2 导出能力

第一版必须支持：

- 导出 PDF
- 导出 Word
- 导出原始 JSON

### 11.3 质量要求

- 模板在桌面端编辑预览稳定
- PDF 导出格式不跑版
- Word 导出后可继续基本编辑

## 12. 非功能需求

### 12.1 性能

- 首屏在常规网络下快速可用
- 编辑与模板预览保持流畅
- AI 请求需有明确加载态和失败提示

### 12.2 隐私

- 默认不要求 C 端用户上传长期个人数据
- 明确提示本地保存机制
- 导出前不产生额外隐式分享链接

### 12.3 可观测性

- AI 请求日志
- 评分耗时日志
- 导出任务日志
- 关键错误监控

### 12.4 可扩展性

第二阶段可平滑扩展：

- C 端登录
- 云端保存
- 多端同步
- 英文简历
- 企业多角色权限体系

## 13. 风险与应对

### 13.1 匿名模式的数据丢失风险

风险：用户清理浏览器缓存后，本地草稿可能丢失。

应对：

- 强提示用户导出 JSON 备份
- 增加自动保存状态提示
- 提供导入恢复能力

### 13.2 LLM 输出不稳定

风险：不同模型输出风格和结构可能波动。

应对：

- 所有输出经过 schema 校验
- 对关键任务采用模板化 prompt 和后处理
- 失败自动降级或要求重试

### 13.3 PDF/Word 导出一致性问题

风险：多模板导出容易出现排版差异。

应对：

- 采用统一渲染中间层
- 首版控制模板数量
- 对导出结果建立回归校验样本

## 15. 验收标准

第一版完成时，应满足以下验收条件：

- 用户不登录即可完整使用 C 端核心流程
- 用户可新建、编辑、保存、导入、导出简历
- 用户可通过 AI 完成生成、润色、关键词增强
- 用户可得到 ATS 与 JD 匹配评分报告
- 用户可导出稳定的 PDF/Word
- B 端可管理岗位并对简历进行协作评审

## 16. 结论

ResumeLM 第一版应以匿名开放、低门槛、高实用为核心，优先服务校招用户最常见的“快速出简历、快速优化、快速导出”路径。通过本地保存替代登录和匿名云端存储，可以把研发资源集中在真正构成产品差异化的 AI 生成、评分和导出体验上，同时为第二阶段的登录与云端体系留下明确演进空间。
